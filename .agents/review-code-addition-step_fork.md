## 1. Findings (Suspected Bugs, Spec Mismatches, and Correctness Risks)

No bug was found that invalidates `exact_match` or leaks ground-truth answers to the predicting position. The four findings below cover one deliberate teacher-forced evaluation subtlety that moves non-`exact_match` metrics relative to free-running outer-loop rollout, one cross-variant loss/gradient scaling asymmetry against `cls`, silent configuration no-ops, and minor split/seed configuration traps.

### Finding 1 (Medium — Metric Semantics vs Outer-Loop Rollout): `evaluate_step_fork` teacher-forces inter-column state (`c_k`, `o_0..o_{k-1}`) across all `K + 1` columns; `exact_match` and `FirstErrorType` match greedy rollout, but headline `step_accuracy` (in `eval.json`) and diagnostic accuracies do not

- **Where**:
  - Teacher-forced evaluation in [evaluation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_fork/evaluation.py#L52-L67) (`evaluate_step_fork`)
  - Unused free-running outer-loop rollout in [generation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_fork/generation.py#L39-L68) (`rollout_step_fork`, called only from tests, never from [run.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_fork/run.py#L15-L49) or [train_and_evaluate.py](file:///atelier/code/workshop/yessir/experiments/addition/train_and_evaluate.py#L162-L183))
  - Specified intentionally in [task.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/task.md#L143-L150) and [step_fork.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/variants/step_fork.md#L88-L96), vs the outer-loop rollout check in [reviewer-code.md](file:///atelier/code/workshop/yessir/.agents/reviewer-code.md#L34).
- **Expectation vs actual behaviour**:
  - [reviewer-code.md](file:///atelier/code/workshop/yessir/.agents/reviewer-code.md#L34) asks whether step `k + 1` in `evaluation.py` receives the model's own predicted state (`c_{k+1}` and `o_0..o_k`) and stops on the model's own halt decision with no access to the reference trajectory after problem setup.
  - By explicit design in [task.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/task.md#L143-L150) (to keep step denominators identical to single-pass full-trace `ar` and `addressed_ar`), `evaluate_step_fork` calls `reference_add(prob.alphabet, prob.a, prob.b)` up front and builds all `3 * (K + 1)` branched queries using the **oracle** `step.carry_in` and **oracle** `sum_digits[:k]`.
  - **Why `exact_match` and `FirstErrorType` remain valid**: Within column `k`, `step_fork`'s three branches (`[S]`, `[C]`, `[F]`) are separate sequences that do not condition on one another. Across columns `0 .. k_err` up to the earliest error `k_err`, every prior step `j < k_err` satisfied `(pred_o[j], pred_c[j], pred_flag[j]) == (o_j, c_{j+1}, flag_j)` (in particular `pred_flag[j] == FLAG_CONTINUE`), so the oracle prefix `(step.carry_in, sum_digits[:k])` fed into `evaluate_step_fork` at `0 <= k <= k_err` is token-for-token identical to the free-running prefix `(carry, output)` in `rollout_step_fork`. Therefore, in exact arithmetic, `exact_match` and all four `FirstErrorType` rates equal free-running greedy rollout.
  - **Where teacher forcing diverges from rollout**:
    1. *Post-error state resetting*: After any mistake at column `k_err` (wrong `c_{k+1}`, wrong `o_k`, or premature `FLAG_FINISHED`), `evaluate_step_fork` resets column `k_err + 1` to the ground-truth carry and output history and keeps scoring through column `K`.
    2. *Halting token semantics on `k < K`*: In `rollout_step_fork` ([generation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_fork/generation.py#L64)), rollout stops only when `flag_k == SpecialToken.FLAG_FINISHED` (`0xF6`), treating all other 255 byte ids (e.g. `[F] = 0xFA` self-copy) as non-halting continuation. In `evaluate_step_fork` ([evaluation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_fork/evaluation.py#L103)), `halt_ok=(pred_flag == int(step.flag))` requires exact `FLAG_CONTINUE` (`0xF5`) on every `k < K`, matching [step_fork.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/variants/step_fork.md#L96).
    3. *Minor spec note on floating-point precision*: [task.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/task.md#L145) notes that `"under bfloat16 autocast, differences in padding and batch shape can flip near-tied argmax decisions"`. Nothing in `yessir/` or `experiments/` uses `bfloat16` autocast (training and evaluation run entirely in `float32`), though even in `float32`, GEMM/SDPA reduction tiling between an unpadded 3-row batch (`rollout_step_fork`) and a right-padded `3 * batch_size` batch (`evaluate_step_fork`) shifts logits by up to `~4.8e-7` (verified empirically on CPU).
- **Concrete input that triggers it**:
  - Consider `alphabet = b"0123456789"`, `a = b"5999"` (`9995`), `b = b"5000"` (`0005`), whose sum `10000` (`b"00001"`) ripples a carry across `K + 1 = 5` columns (`k = 0..4`). If a model fails carry generation at `k = 0` (`pred_o[0] = '0'`, `pred_c[0] = '0'` instead of `'1'`, `pred_flag[0] = FLAG_CONTINUE`)—or emits `pred_flag[0] = FLAG_FINISHED` at `k = 0`—while accurately executing carry propagation when handed `c_k = '1'`, free-running `rollout_step_fork` fails columns `1..4` (getting `9990` in 4 steps, or halting after 1 step), whereas `evaluate_step_fork` feeds oracle `c_k = '1'` into `k = 1..4` and reports `step_accuracy = 4 / 5 = 0.80` and `carry_accuracy = 4 / 5 = 0.80`.
- **Plausible impact on headline or diagnostic numbers**:
  - **Does not move `exact_match`** or `FirstErrorType` rates (beyond `~5e-7` `float32` ties).
  - **Moves `step_accuracy` (written to `eval.json` alongside `exact_match`)**, `digit_accuracy`, `carry_accuracy`, and `halt_accuracy` upward relative to free-running execution on partially accurate models (notably on `extrap_len` `L = 21..40` and [carry-chain-injection.json](file:///atelier/code/workshop/yessir/studies/addition/carry-chain-injection.json)). Claims citing `step_accuracy` or `carry_accuracy` must treat them as *single-step teacher-forced conditional accuracy*, not rollout prefix accuracy.

### Finding 2 (Low — Cross-Variant Loss & Gradient Scale vs `cls`): `step_fork` averages cross-entropy over `3 * batch_size` targets (`1:1` parity with `step_ar`), whereas `cls` sums across its 3 heads (`3x` larger loss and gradient norm)

- **Where**:
  - `next_token_cross_entropy` in [training.py](file:///atelier/code/workshop/yessir/yessir/training.py#L151-L184) and `train_step` ([training.py](file:///atelier/code/workshop/yessir/yessir/training.py#L229-L240)), invoked with `train_batch_size = 3 * config.batch_size` in [run.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_fork/run.py#L47)
  - `parallel_classification_cross_entropy` in [training.py](file:///atelier/code/workshop/yessir/yessir/training.py#L98-L148), invoked with `batch_size = config.batch_size` in [run.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/cls/run.py#L40-L45)
  - Relevant study: [variants-comparison.json](file:///atelier/code/workshop/yessir/studies/addition/variants-comparison.json).
- **Expectation vs actual behaviour**:
  - For `B = config.batch_size` sampled column transitions:
    - `step_fork` collates `3 * B` sequences with `1` non-ignored target each, so `next_token_cross_entropy` (`F.cross_entropy(..., ignore_index=-100)` with default `reduction="mean"`) computes `(1 / (3 * B)) * sum_{i=1}^{B} (CE_S[i] + CE_C[i] + CE_F[i])`.
    - `step_ar` collates `B` sequences with `3` non-ignored targets each, computing the exact same `(1 / (3 * B))` mean over `3 * B` target tokens.
    - `cls` collates `B` sequences and **sums** the per-head batch means across `H = 3` heads (`(1 / B) * sum_{i=1}^{B} (CE_0[i] + CE_1[i] + CE_2[i])`), which is **`3x` larger** than the `(1 / (3 * B))` mean used by `step_fork` and `step_ar`.
- **Concrete config that triggers it**:
  - Default `AdditionStepForkConfig(batch_size=64)` vs `AdditionClsConfig(batch_size=64)` in [variants-comparison.json](file:///atelier/code/workshop/yessir/studies/addition/variants-comparison.json). Under uniform random predictions (`CE = ln(256) ≈ 5.545`), `cls` logs `loss ≈ 16.636` in `train.jsonl` (`nats/step`), whereas `step_fork` logs `nats/token` (`~1/3` scale once self-copy bias subsides).
- **Plausible impact on headline or diagnostic numbers**:
  - **Training loss curves (`train.jsonl` / `web/`)**: `cls` loss and `step_fork` loss differ by a factor of `3` by definition and cannot be overlaid without dividing `cls` loss by `3`.
  - **Optimiser dynamics**: Because `build_optimizer` ([training.py](file:///atelier/code/workshop/yessir/yessir/training.py#L81-L95)) uses `AdamW(lr=3e-4, betas=(0.9, 0.95), eps=1e-8, weight_decay=0.0)`, multiplying gradients by `3` cancels in `m_hat / sqrt(v_hat)` whenever `sqrt(v_hat) >> 1e-8`, but shrinks the effective denominator floor in `cls` from `eps = 1e-8` to `eps / 3 ≈ 3.33e-9` once gradients vanish near `loss -> 0.0000` (relevant only to extreme 500k-step overtraining in [grokking-and-overtraining.json](file:///atelier/code/workshop/yessir/studies/addition/grokking-and-overtraining.json)). Unlikely to move headline accuracy.

- **Ground-truth addition oracle** ([reference.py](file:///atelier/code/workshop/yessir/experiments/addition/reference.py#L69-L186)):
  - Verified `_validate_inputs`, `_compute_step`, `reference_step`, and `reference_add` by hand against [task.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/task.md#L13-L70) across:

- **Sampling distributions** ([inputs.py](file:///atelier/code/workshop/yessir/experiments/addition/inputs.py#L403-L549), [alphabet.py](file:///atelier/code/workshop/yessir/yessir/alphabet.py#L22-L70)):

  - Carry-chain injection (`p_chain`, [inputs.py](file:///atelier/code/workshop/yessir/experiments/addition/inputs.py#L441-L450)) triggers with probability `p_chain` when `min(L_a, L_b) >= 2`, picking length `m in 1 .. min(L_a, L_b) - 1` and start `i in 0 .. min(L_a, L_b) - 1 - m`, setting `v_a[i] + v_b[i] >= B` and `v_a[j] + v_b[j] == B - 1` for `j in i + 1 .. i + m` with all index bounds exact. (Minor note: two-stage sampling `a_vals[i] ~ U(1..B-1)`, `b_vals[i] ~ U(B-a_vals[i]..B-1)` makes `b_vals[i]` slightly heavier near `B - 1` than `a_vals[i]`, while strictly satisfying `v_a + v_b >= B`.)
  - Step sampling (`iter_problem_steps`, [inputs.py](file:///atelier/code/workshop/yessir/experiments/addition/inputs.py#L533-L549)) uses a dedicated `random.Random(f"{seed}:step")` decoupled from `iter_problems`'s `random.Random(seed)`, selecting `k = K` with probability `p_terminal` and `randint(0, K)` otherwise, matching [task.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/task.md#L80) verbatim.
- **Train/eval disjointness & RNG separation**:
  - `AdditionConfig` rejects `eval_seed == seed` ([config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L289-L292)) and strips any training base from `eval_ood_bases` ([config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L173-L184)).
  - `ood_base{b}` splits are strictly disjoint from training by `len(alphabet) == b`; `extrap_len` (`min_length = max_length + 1`) is strictly disjoint from training by operand lengths `L_a, L_b > max_length`; `permuted` is strictly alphabet-disjoint from `p_prior=1.0` canonical training (`alphabet != canonical`).
  - Both training and evaluation generators instantiate local `random.Random` objects rather than touching global `random` or `torch` RNG state, so mid-training evaluations (`eval_every`) leave the training stream and model updates bit-identical ([test_run.py](file:///atelier/code/workshop/yessir/experiments/addition/tests/test_run.py#L483-L580)).

### 2.2 Tokenisation, Sequence Layout, and Causal / Padding Isolation
- **Exact sequence layout & position coupling** ([variants/step_fork/inputs.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_fork/inputs.py#L25-L149), [inputs.py](file:///atelier/code/workshop/yessir/experiments/addition/inputs.py#L206-L244)):
  - Verified against [step_fork.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/variants/step_fork.md#L11-L75):
    - `[BOS]` (`0xF2`, `SPECIAL=0`, `pos=0`), `alphabet` (`s_0..s_{B-1}`, `ALPHABET=1`, `pos=0..B-1`), `[SEP]` (`0xF0`, `SPECIAL=0`, `pos=0`), `a` (`OPERAND_A=2`, `pos=0..L_a-1`), `[SEP]` (`0, 0`), `b` (`OPERAND_B=3`, `pos=0..L_b-1`), `[SEP]` (`0, 0`), `c_k` (`CARRY=4`, `pos=k`), `[SEP]` (`0, 0`), `o_0..o_{k-1}` (`OUTPUT=5`, `pos=0..k-1`), and trailing query token `[S]=0xF8` / `[C]=0xF9` / `[F]=0xFA` (`SPECIAL=0`, `pos=k`).
    - At every column `k` (`0 <= k <= K`), `[S]`/`[C]`/`[F]` sits at `position_id = k`, aligning at zero offset with `a_k` (when `k < L_a`), `b_k` (when `k < L_b`), and `c_k` (`CARRY`), while historical outputs `o_j` sit at `0 .. k - 1`.
- **Zero target leakage**:
  - Each branch `LabelledExample` of length `P_k` has `labels = (IGNORE_INDEX,) * (P_k - 1) + (target,)` ([variants/step_fork/inputs.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_fork/inputs.py#L144-L149)), where `target` is `o_k`, `c_{k+1}`, or `int(flag_k)`. None of `(o_k, c_{k+1}, flag_k)` or steps `> k` appears in `input_ids`, and `next_token_cross_entropy` ([training.py](file:///atelier/code/workshop/yessir/yessir/training.py#L151-L184)) supervises `labels[b, P_k - 1]` directly against `logits[b, P_k - 1]` without internal shifting.
- **Right-padding, causal masking, and `EmbeddingMode` train/eval parity**:
  - `collate` and `collate_labelled` ([batch.py](file:///atelier/code/workshop/yessir/yessir/batch.py#L59-L154)) right-pad `input_ids` with `SpecialToken.PAD` (`0xF1`), `token_type_ids` and `position_ids` with `0`, and `labels` with `IGNORE_INDEX = -100`.
  - `MultiHeadSelfAttention` ([blocks.py](file:///atelier/code/workshop/yessir/yessir/blocks.py#L111)) uses `F.scaled_dot_product_attention(..., is_causal=True)`. Because real tokens occupy `0 .. lengths[b] - 1` and `PAD` tokens occupy `>= lengths[b]`, real positions never attend to `PAD`, `RMSNorm` and `SwiGLUFeedForward` act strictly per-position, training masks all positions except `lengths[b] - 1` with `-100`, `evaluate_step_fork` indexes `logits[row_indices, batch.lengths - 1]` ([evaluation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_fork/evaluation.py#L86-L87)), and `rollout_step_fork` collates 3 equal-length branches of a single problem (`lengths == [P_k, P_k, P_k]`, zero padding) and indexes `logits[:, -1, :]` ([generation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_fork/generation.py#L60)).
  - `make_example` ([inputs.py](file:///atelier/code/workshop/yessir/experiments/addition/inputs.py#L171-L203)) and `SubspaceEmbedding.forward` ([embedding.py](file:///atelier/code/workshop/yessir/yessir/embedding.py#L119-L128)) enforce identical `token_type_ids` / `position_ids` presence across training, evaluation, and rollout for all three `EmbeddingMode`s (`TOKEN_TYPE_PE`, `TOKEN_TYPE_NOPE`, `NOPE`).

### 2.4 Evaluation, Error Taxonomy, Rollout Resilience, and Batch Isolation
- **Arbitrary vocabulary token handling (`0..255`)**:
  - Because `SubspaceLMHead` produces logits over all 256 byte tokens, `[S]`, `[C]`, and `[F]` can emit out-of-alphabet bytes or special tokens (`0xF0..0xFF`).
  - In `evaluate_step_fork` ([variants/step_fork/evaluation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_fork/evaluation.py#L97-L105)) + `score_predictions` ([addition/evaluation.py](file:///atelier/code/workshop/yessir/experiments/addition/evaluation.py#L78-L222)):
    - Any `pred_o` or `pred_c` outside `alphabet` (including `0xF0..0xFF`) is classified as `FirstErrorType.OUT_OF_ALPHABET` (checked in `(sum_digit, carry_out)` order).
    - Any wrong in-alphabet `pred_o` or `pred_c` (including `s_2..s_{B-1}` on the carry branch) is classified as `PRIOR_INTRUSION` if `set(alphabet) == set(SymbolSet.HEX[:B])` and `pred_token == SymbolSet.HEX[digit_value]` (which can never fire on an unpermuted ascending canonical alphabet because `HEX[digit_value] == expected_token`), and `PROCEDURAL_ERROR` otherwise.
    - When `pred_o == o_k` and `pred_c == c_{k+1}`, any wrong `pred_flag` (whether premature `FLAG_FINISHED`, missing `FLAG_FINISHED` at `k = K`, or an arbitrary non-flag byte like `[F]`) sets `halt_ok=False` and classifies the problem as `SYNTAX_MALFORMATION`.
    - `exact_match + out_of_alphabet + prior_intrusion + procedural_error + syntax_malformation == 1.0` holds identically.
  - In `rollout_step_fork` ([generation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_fork/generation.py#L39-L68)):
    - Emitting arbitrary `0..255` tokens on `[S]` or `[C]` feeds cleanly into the next step's `build_step_fork_examples` without raising (`Example` accepts all `0..255` token ids), and total iterations are hard-capped at `max(len(a), len(b)) + 1`.
- **Eval mode & statelessness**:
  - Both `evaluate_step_fork` and `rollout_step_fork` are decorated with `@torch.no_grad()`, call `model.eval()` before forward passes, carry zero state across batches/chunks, and `train_step` ([training.py](file:///atelier/code/workshop/yessir/yessir/training.py#L225)) restores `model.train()` on the next optimisation step.
