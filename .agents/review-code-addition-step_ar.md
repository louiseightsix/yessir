## 2. Findings (Suspected Bugs, Spec Mismatches, and Correctness Risks)

### Finding 1 [Medium — Evaluation & Metric Semantics]: Intra-step and inter-step teacher forcing in `evaluate_step_ar`

- **Where**: [evaluation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/evaluation.py#L59-L129), [run.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/run.py#L36-L49), [generation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/generation.py#L17-L82), [task.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/task.md#L143-L150), [step_ar.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/variants/step_ar.md#L104-L112).
- **Expectation vs actual behaviour**:
  - `.agents/reviewer-code.md` asks whether multi-step evaluation feeds the model's own predicted state (`o_k`, `c_{k+1}`) into step `k + 1` and stops on the model's own halt decision without reference leakage.
  - A genuine free-running outer-and-inner-loop decoder exists in [rollout_step_ar](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/generation.py#L17-L82), **but `run_addition_step_ar` never calls it**. All metrics written to `eval.json`, `eval.jsonl`, and `eval_splits.json` come exclusively from [evaluate_step_ar](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/evaluation.py#L26-L129), which intentionally implements teacher-forced evaluation across all `K + 1` oracle steps as documented in `task.md` §3 and `step_ar.md` §4.
  - Crucially, `evaluate_step_ar` teacher-forces at **two levels**:
    1. **Intra-step teacher forcing (within column `k`)**: Lines [64-77](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/evaluation.py#L64-L77) pass the **oracle** pair `(t_0, t_1) = pack_step_order(step.sum_digit, step.carry_out, order)` into `build_step_ar_example` and read `preds_t0`, `preds_t1`, and `preds_flag` from a single forward pass ([lines 98-107](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/evaluation.py#L98-L107)).
    2. **Inter-step teacher forcing (across columns `0 .. K`)**: Lines [63-77](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/evaluation.py#L63-L77) feed oracle `step.carry_in` and oracle `sum_digits[:k]` into every column `k` regardless of whether column `k - 1` predicted the wrong carry or emitted a premature `FLAG_FINISHED`.
- **Why headline `exact_match` and `FirstErrorType` are unaffected**:
  - Attention in [MultiHeadSelfAttention](file:///atelier/code/workshop/yessir/yessir/blocks.py#L111) is strictly causal (`is_causal=True`), right-padding in [collate](file:///atelier/code/workshop/yessir/yessir/batch.py#L91-L98) sits strictly after every real position (`>= lengths[b]`), all computation runs in `float32`, and [classify_first_error](file:///atelier/code/workshop/yessir/experiments/addition/evaluation.py#L132-L154) inspects predictions in exact emission order (`t_0`, then `t_1` via `step_order`, then `halt_ok`).
  - Consequently, up to the **earliest** token mismatch on a problem, the prefix seen by `evaluate_step_ar` is bit-for-bit identical to the prefix seen by `rollout_step_ar`. `exact_match` is `1` iff zero mismatches occur across all `3 * (K + 1)` predictions, and `FirstErrorType` classifies that exact first mismatch. (Confirmed empirically across all 12 `(EmbeddingMode, StepOrder, use_query_tokens)` combinations.)
- **How secondary and diagnostic numbers move (concrete verified example)**:
  1. **`digit_accuracy` asymmetry between `carry_first` and `sum_first` ([step-order.json](file:///atelier/code/workshop/yessir/studies/addition/step-order.json#L1-L8))**: Under `SUM_FIRST`, `pred_o[k]` is `preds_t0` (conditioned only on the step prompt). Under `CARRY_FIRST`, `pred_o[k]` is `preds_t1`, which in `evaluate_step_ar` conditions on the **oracle** `c_{k+1}` at `t_0` even when `preds_t0` (`pred_c[k]`) was wrong! Note that `step_accuracy` and `carry_accuracy` require `both_ok = (pred_o == o_k) and (pred_c == c_{k+1})` ([evaluation.py](file:///atelier/code/workshop/yessir/experiments/addition/evaluation.py#L196-L204)), so they are **immune** to intra-step `t_0 -> t_1` leakage, whereas `digit_accuracy` (`pred.sum_digit == step.sum_digit`) is directly inflated under `CARRY_FIRST`.
  2. **`halt_accuracy` inflation in `step_ar` vs `cls` / `step_fork` ([step-sampling.json](file:///atelier/code/workshop/yessir/studies/addition/step-sampling.json#L1-L8), [variants-comparison.json](file:///atelier/code/workshop/yessir/studies/addition/variants-comparison.json#L1-L8))**: At the critical column `k = max(L_a, L_b) - 1`, halting is `FLAG_FINISHED` iff `c_{k+1} == s_0` ([reference.py](file:///atelier/code/workshop/yessir/experiments/addition/reference.py#L116-L120)). In `cls` and `step_fork`, the model must compute whether the column carries out on its own to predict `flag_k`. In `evaluate_step_ar`, `preds_flag` (`offsets[2] = -1`) attends directly to the **oracle** `c_{k+1}` token already placed at `(TokenType.CARRY, k + 1)`! A model that mispredicts `c_{k+1} = s_0` on an overflow problem halts prematurely in `rollout_step_ar`, yet sees oracle `c_{k+1} = s_1` in `evaluate_step_ar` and scores `halt_accuracy = 1.0`.
  3. **Concrete Python probe (`alphabet = b"0123456789"`, `a = b"7"`, `b = b"5"` -> `7 + 5 = 12`, `K = 1` overflow, `StepOrder.CARRY_FIRST`)**: Consider a model whose carry threshold fails (`pred_c[0] = '0'` instead of `'1'`), whose sum circuit computes `(v_a + v_b - 10 * v_{c_out_in_context})`, and whose halt circuit outputs `FLAG_FINISHED` iff `k >= max(L_a, L_b) - 1` and `c_{out_in_context} == '0'`. Verified via `./yessir.sh uv run --no-sync python`:
     - Free-running `rollout_step_ar` emits `[('9', '0', FLAG_FINISHED)]` (`1` step instead of `2`: wrong digit `'9'` instead of `'2'`, premature halt at `k = 0`, missing MSD `'1'`). Free-running digit accuracy is `0/2 = 0.0`, free-running halt accuracy is `0.0`.
     - `evaluate_step_ar` feeds oracle `c_1 = '1'` into `t_0` at `k = 0` and runs `k = 1` with `c_1 = '1'`, reporting `exact_match = 0.0`, `step_accuracy = 0.0`, `carry_accuracy = 0.0`, **`digit_accuracy = 0.5`**, and **`halt_accuracy = 1.0`**.
  4. **Inter-step reset on `step_accuracy` (in `eval.json`) and `carry_accuracy` ([carry-chain-injection.json](file:///atelier/code/workshop/yessir/studies/addition/carry-chain-injection.json#L1-L8))**: On a 5-column carry ripple such as `99999 + 1 = 100000` (`a = b"99999", b = b"1", K = 5`), a model that propagates carries (`9 + 0 + 1 = 10`) but fails initial carry generation (`9 + 1 + 0 -> sum '0', carry '0'`) gets `5` of `6` columns wrong in free-running rollout (`09999` instead of `000001`), yet scores `step_accuracy = 5/6 = 83.33%` and `carry_accuracy = 5/6 = 83.33%` in `evaluate_step_ar` because oracle `carry_in = '1'` is re-injected at `k = 1..5`. Any study text citing `step_accuracy` or `carry_accuracy` must describe them strictly as *per-column oracle-state transition accuracy*, never rollout accuracy.

### Finding 2 [Low — Diagnostic Metric Confounder]: Pooled `B = 2` in `permuted` split inflates `prior_intrusion`

- **Where**: [config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L402-L415), [evaluation.py](file:///atelier/code/workshop/yessir/experiments/addition/evaluation.py#L90-L102), [train_and_evaluate.py](file:///atelier/code/workshop/yessir/experiments/addition/train_and_evaluate.py#L182), [task.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/task.md#L162), [prior-override.json](file:///atelier/code/workshop/yessir/studies/addition/prior-override.json#L1-L8).
- **Expectation vs actual behaviour**:
  - `task.md` §3 (`line 162`) explicitly warns: *"In base `B = 2` the only wrong in-alphabet symbol is the canonical one, so every in-alphabet value error on a permuted canonical alphabet is counted as `prior_intrusion` and none as `procedural_error`; there the rate carries no evidence of a prior. Read `prior_intrusion` as evidence of a canonical-order prior only for `B >= 3`..."*
  - However, `AdditionConfig.eval_splits()` ([config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L402-L415)) creates only a single aggregate `"permuted"` split with `bases = train_bases` (default `(2, 4, 8, 10)`), and `train_and_evaluate` ([line 182](file:///atelier/code/workshop/yessir/experiments/addition/train_and_evaluate.py#L182)) writes only pooled split-level averages to `eval_splits.json`.
- **Concrete trigger & impact**:
  - Under `AdditionStepArConfig(p_prior=0.5, eval_permuted_canonical=True)` (default `bases="2,4,8,10"`), `~25%` of the 200 problems in `permuted` have `B = 2`, where [sample_problem](file:///atelier/code/workshop/yessir/experiments/addition/inputs.py#L418-L425) deterministically produces `alphabet = (ord('1'), ord('0'))`.
  - In [_classify_value_mismatch](file:///atelier/code/workshop/yessir/experiments/addition/evaluation.py#L98-L100), any in-alphabet wrong digit or carry on `B = 2` necessarily equals `SymbolSet.HEX[digit_value]`, yielding `100%` `prior_intrusion` and `0%` `procedural_error`.
  - Even for a model with `p_prior = 0.0` and zero canonical prior, uniform random in-alphabet errors across `bases = (2, 4, 8, 10)` produce a `prior_intrusion / (prior_intrusion + procedural_error)` share of `(1 + 1/3 + 1/7 + 1/9) / 4 = 0.3968` (`~39.7%`), and up to `100%` if arithmetic errors concentrate on `B = 2` (which has the longest binary carry chains). Because `eval_splits.json` stores no per-base breakdown, a reader cannot filter to `B >= 3` post hoc unless the study excludes `2` from `bases` or runs per-base evaluations.
  - Note also that `eval_permuted_canonical` defaults to `False` ([config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L158)), so runs in `prior-override.json` must explicitly pass `--eval-permuted-canonical` or no `permuted` split will be recorded at all.

### Finding 3 [Low — Config Interaction]: `fixed_d_model=True` silently overrides `d_scratch=0` under `token_type_nope` and `nope`

- **Where**: [config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L121-L122), [config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L331-L340), [config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L425-L436), [harness-vs-capacity.json](file:///atelier/code/workshop/yessir/studies/addition/harness-vs-capacity.json#L1-L8).
- **Expectation vs actual behaviour**:
  - `AdditionConfig.effective_d_scratch` ([lines 331-340](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L331-L340)) adds `dropped_token_type` (`16`) and `dropped_position` (`d_position`, default `32`) to `self.d_scratch` whenever `self.fixed_d_model` is `True` (the default).
  - That design is intentional and documented for `EmbeddingMode` ablations ([task.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/task.md#L133)), so `d_model` stays `512` across `token_type_pe`, `token_type_nope`, and `nope`. However, in capacity/scratchpad sweeps ([harness-vs-capacity.json](file:///atelier/code/workshop/yessir/studies/addition/harness-vs-capacity.json#L5), [minimum-model-size.json](file:///atelier/code/workshop/yessir/studies/addition/minimum-model-size.json#L5)), setting `d_scratch=0` without also setting `fixed_d_model=False` does **not** zero out the scratchpad in non-PE modes.
- **Concrete trigger**:
  - `AdditionStepArConfig(embedding_mode="nope", d_scratch=0)` leaves `fixed_d_model=True`, giving `effective_d_scratch = 0 + 16 + 32 = 48` (`d_model = 304`) instead of `0` (`d_model = 256`). Under `embedding_mode="token_type_nope", d_scratch=0`, `effective_d_scratch = 32`. Moreover, `derived_summary()` ([lines 425-436](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L425-L436)) and `config.json` record `d_model` and `d_scratch=0`, never printing `effective_d_scratch=48`.
  - Similarly, on [AdditionStepConfig](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L443-L446), `p_terminal` (`default=0.2`) is ignored whenever `all_steps=True` ([inputs.py](file:///atelier/code/workshop/yessir/experiments/addition/inputs.py#L537-L547)): passing `--all-steps --p-terminal 0.5` raises no warning or error and leaves `p_terminal: 0.5` in `config.json` as a no-op.

### Finding 4 [Low / Edge-Case — RNG Seed Collision]: `_split_seed` `+1` bump can collide adjacent `ood_base*` splits or shift one split across a seed sweep

- **Where**: [config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L353-L356), [config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L374-L386).
- **Expectation vs actual behaviour**:
  - `_split_seed(offset)` computes `candidate = self.eval_seed + offset` and returns `candidate + 1 if candidate == self.seed else candidate`, with offsets `0` (`id`), `1000 + b` (`ood_base{b}`), `2000` (`extrap_len`), and `3000` (`permuted`).
  - Two edge cases arise:
    1. **OOD-to-OOD split seed collision**: Because `ood_base{b}` uses consecutive offsets `1000 + b`, bumping `candidate` by `+1` when `self.seed == self.eval_seed + 1000 + b` makes `ood_base{b}`'s seed equal `self.eval_seed + 1000 + (b + 1)` — the exact seed of `ood_base{b+1}`!
    2. **Cross-seed evaluation set drift**: In a multi-seed training sweep (`seed-stability.json`) with fixed `eval_seed=999`, every training `seed` is supposed to be evaluated on the exact same 200 problems per split. If one run in the sweep happens to pick `seed` in `{2002, 2011, 2999, 3999}`, `_split_seed` silently shifts that run's `ood_base3`, `ood_base12`, `extrap_len`, or `permuted` seed by `+1`, evaluating it on 200 completely different problems than the other seeds in the sweep.
- **Concrete trigger**:
  - `AdditionStepArConfig(bases="2,10", eval_ood_bases="3,4", eval_seed=999, seed=2002).eval_splits()` assigns `seed = 2003` to **both** `ood_base3` and `ood_base4`, so both splits draw from `random.Random(2003)` (identical `rng.choice((b,))` call pattern, correlated uniform draws for lengths, carry-chain triggers, and digit rank fractions).

### Finding 5 [Minor — Rollout Helper, Spec Precision Note & CLI Formatting]: Non-strict continuation and `N + 1` cap in `rollout_step_ar`, `bfloat16` spec drift, and `AdditionToken` hex display

1. **`rollout_step_ar` continues on malformed `flag_k` tokens and stops at `max_columns` without a separate halted indicator** ([generation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/generation.py#L37-L82)):
   - At line [77](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/generation.py#L77), `rollout_step_ar` breaks only on `if flag_k == SpecialToken.FLAG_FINISHED:`. If an undertrained model emits an ordinary digit (e.g. `ord('0')`) or `[SEP]` at the third step position instead of `FLAG_CONTINUE`, `rollout_step_ar` treats it identically to `FLAG_CONTINUE` and advances to step `k + 1` (whereas `evaluate_step_ar` at [line 124](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/evaluation.py#L124) checks `pred_flag == int(step.flag)` and marks `halt_ok = False`).
   - Furthermore, `max_columns = max(len(a_tokens), len(b_tokens)) + 1` ([line 37](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/generation.py#L37)) caps execution at `N + 1` steps. On an overflow problem (`K = N`, which genuinely has `N + 1` steps), a model that never emits `FLAG_FINISHED` stops after `N + 1` steps anyway; callers inspecting `rollout_step_ar` output must check `steps[-1][2] == SpecialToken.FLAG_FINISHED` rather than comparing `[o for o, _, _ in steps]` alone.
2. **Spec drift on `bfloat16` autocast** ([task.md](file:///atelier/code/workshop/yessir/experiments/addition/spec/task.md#L145)):
   - `task.md` §3 notes parenthetically that *"under `bfloat16` autocast, differences in padding and batch shape can flip near-tied `argmax` decisions"*. In the live repo (unlike `.prototypes/transformadder/`), neither `yessir/` nor `experiments/addition/` uses `bfloat16` or `torch.autocast`: [SubspaceEmbedding](file:///atelier/code/workshop/yessir/yessir/embedding.py#L82), [train_step](file:///atelier/code/workshop/yessir/yessir/training.py#L205), and [evaluate_step_ar](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/evaluation.py#L87) execute strictly in `float32`.
3. **Inspection CLI prints `AdditionToken`s (`[S]`, `[C]`, `[F]`, `[IDX]`) as raw hex bytes** ([inspect_data.py](file:///atelier/code/workshop/yessir/yessir/inspect_data.py#L14-L21)):
   - `format_token` resolves `SpecialToken` (`0xF0..0xF7`), so `[BOS]`, `[SEP]`, `[FLAG_CONTINUE]`, and `[FLAG_FINISHED]` print by name, but `AdditionToken` (`0xF8..0xFB`, in `EXPERIMENT_SPECIAL_RANGE`) falls through to `f"0x{token:02x}"`. Running `python -m experiments.addition.variants.step_ar.dataset --use-query-tokens` therefore prints `[S]`, `[C]`, `[F]` as `0xf8`, `0xf9`, `0xfa`, visually indistinguishable in style from symbol-pool hex bytes `0x00..0xef`.

## 3. What Was Read and Verified Correct

### 3.1 Data Generation & Reference Oracle

- **Reference arithmetic** ([reference.py](file:///atelier/code/workshop/yessir/experiments/addition/reference.py#L38-L186)):
  - `_validate_inputs` delegates alphabet uniqueness, `SYMBOL_RANGE` (`0x00..0xEF`) membership, and `B >= 2` checks to [create_alphabet](file:///atelier/code/workshop/yessir/yessir/alphabet.py#L22-L70), rejects empty `a` or `b`, and verifies every operand byte belongs to `alphabet`.
  - `_compute_step` maps `s_i -> i`, substitutes `0` when `k >= len(a)` or `k >= len(b)`, enforces `carry in {s_0, s_1}` (plus unreachable-state guards `carry == s_0` at `k == 0` and `carry == s_1` at overflow column `k == max(len(a), len(b))`), computes `sum_digit = alphabet[total % B]` and `carry_out = alphabet[total // B]`, and sets `flag = FLAG_FINISHED` iff `k >= n - 1 and carry_out == s_0`. Because `total <= (B - 1) + (B - 1) + 1 = 2 * B - 1`, `total // B` is always `0` or `1`; at `k == n`, `total = 0 + 0 + 1 = 1 < B` (since `B >= 2`), guaranteeing termination at `K <= n`.
  - **Hand-checked examples**:
    1. `task.md` Example 1 (`alphabet = b"0123456789"`, `a = b"789"`, `b = b"52"`): `k = 0` (`7 + 5 + 0 = 12 -> o_0='2', c_1='1', CONTINUE`), `k = 1` (`8 + 2 + 1 = 11 -> o_1='1', c_2='1', CONTINUE`), `k = 2` (`9 + 0 + 1 = 10 -> o_2='0', c_3='1', CONTINUE`), `k = 3` (`0 + 0 + 1 = 1 -> o_3='1', c_4='0', FINISHED`) -> `b"2101"` (`1012`).
    2. `task.md` Example 2 (`alphabet = b"q#7"`, `a = b"7#"`, `b = b"#"`): `k = 0` (`2 + 1 + 0 = 3 -> o_0='q', c_1='#', CONTINUE`), `k = 1` (`1 + 0 + 1 = 2 -> o_1='7', c_2='q', FINISHED`) -> `b"q7"` (`6`).
    3. Single-column zero (`0 + 0` in base 2, `alphabet = b"ab"`, `a = b"a"`, `b = b"a"`): `1` step (`K = 0`), `(o_0='a', c_1='a', FINISHED)`.
    4. Single-column overflow (`1 + 1` in base 2, `alphabet = b"ab"`, `a = b"b"`, `b = b"b"`): `2` steps (`K = 1`), `[(o_0='a', c_1='b', CONTINUE), (o_1='b', c_2='a', FINISHED)]`.
    5. Leading MSD zeros (`alphabet = b"0123456789"`, `a = b"500"`, `b = b"2"`): `n = 3`, runs `k = 0, 1, 2` before halting (`b"700"`), matching `k >= max(len(a), len(b)) - 1`.
    6. Largest base (`B = 240`, `alphabet = SymbolSet.ALL`) on `(B^3 - 1) + 1`: ripples `3` carries and halts cleanly at `K = 3` (`4` steps).
- **Problem & step sampling distributions** ([inputs.py](file:///atelier/code/workshop/yessir/experiments/addition/inputs.py#L403-L550)):
  - `sample_problem` chooses `base = rng.choice(bases)` uniformly, draws `len_a` and `len_b` independently from `Uniform(min_length..max_length)`, and samples digits uniformly from `0..base - 1`.
  - Under `permuted_canonical=True` ([lines 418-425](file:///atelier/code/workshop/yessir/experiments/addition/inputs.py#L418-L425)), the `while alphabet == canonical:` rejection loop redraws until the shuffled canonical numeral list differs from ascending `SymbolSet.HEX[:base]` (preventing the `1 / B!` unpermuted leak, which would otherwise leave `50%` of `B = 2` problems unpermuted).
  - Under `p_chain > 0` and `min(len_a, len_b) >= 2` ([lines 441-450](file:///atelier/code/workshop/yessir/experiments/addition/inputs.py#L441-L450)), with probability `p_chain` it samples `m ~ Uniform(1 .. n_shared - 1)` and `i ~ Uniform(0 .. n_shared - 1 - m)`, sets column `i` to generate a carry (`a_i ~ Uniform(1 .. B - 1)`, `b_i ~ Uniform(B - a_i .. B - 1)`, so `a_i + b_i >= B`) and the next `m` columns `j in i + 1 .. i + m` to propagate (`a_j ~ Uniform(0 .. B - 1)`, `b_j = B - 1 - a_j`, so `a_j + b_j == B - 1`). *(Minor distributional note: at the carry-origin column `i`, sampling `a_i` uniformly first and `b_i` uniformly from `B - a_i .. B - 1` weights smaller `a_i` slightly less uniformly across the `(a_i, b_i)` triangle `a_i + b_i >= B`, giving `E[a_i] = B / 2` vs `E[b_i] = (3 * B - 2) / 4` — e.g. `5.0` vs `7.0` in base 10. Both are completely valid carry-generating pairs and do not leak anything.)*
  - `iter_problem_steps` ([lines 498-550](file:///atelier/code/workshop/yessir/experiments/addition/inputs.py#L498-L550)) isolates step-index selection onto `step_rng = random.Random(f"{seed}:step")`, so toggling `p_terminal` or `all_steps` leaves the underlying `iter_problems(seed=seed)` sequence invariant. When `all_steps=False`, `P(k == K) = p_terminal + (1 - p_terminal) / (K + 1)` and `P(k == j) = (1 - p_terminal) / (K + 1)` for `0 <= j < K`, matching `task.md` §1.
- **Train/eval disjointness & RNG separation** ([config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L173-L185), [config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L289-L292), [config.py](file:///atelier/code/workshop/yessir/experiments/addition/config.py#L353-L416)):
  - **Unseen bases (`ood_base3`, `ood_base12`)**: `AdditionConfig.__post_init__` strips any base already in `bases` from `eval_ood_bases`, guaranteeing strict base disjointness (`len(alphabet)` never seen in training).
  - **Unseen lengths (`extrap_len`)**: `min_length = self.max_length + 1` (`21..40` by default), so **both** `L_a >= 21` and `L_b >= 21`, strictly exceeding training `max_length = 20`.
  - **In-domain (`id`) and `permuted` overlap rates**: Problems are sampled i.i.d. with separate seeds (`seed=42` vs `eval_seed=999`). For random alphabets from `SymbolSet.ALL` (`240` bytes), even the smallest cell `(B = 2, L_a = 1, L_b = 1)` has `240 * 239 * 4 = 229,440` distinct `(alphabet, a, b)` instances; over `100,000 * 64 = 6.4M` training draws (`~4,000` in that cell), an `id` problem in that cell has `~1.7%` chance of exact collision, and for `B >= 4` or `L >= 2` collision probability is negligible (`< 10^-5`). Under `p_prior = 1.0`, canonical `id` problems have fixed alphabets so very short `(L_a, L_b) = (1, 1)` problems will have been seen in training, whereas `permuted` remains strictly disjoint from `p_prior = 1.0` training (`permuted` guarantees `alphabet != canonical`). At `p_prior = 0.0` with `SymbolSet.ALL`, a random 2-symbol draw hits `('1', '0')` only once in `240 * 239 = 57,360` binary problems (`~28` times across `6.4M` steps).

### 3.4 Evaluation, Outer-Loop Rollout & Error Taxonomy (Variant Question 4)

- **Outer-loop rollout behaviour and malformed-token handling in `rollout_step_ar`** ([generation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/generation.py#L17-L82)):
  - Starts from `(carry = alphabet[0], output = [])` with zero access to `reference_add` or oracle `K` (only `max_columns = max(len(a), len(b)) + 1`, derived solely from input operand lengths).
  - After 3 greedy `argmax` passes emit `(t_0, t_1, flag_k)` and `unpack_step_order` recovers `(o_k, c_next)`, if `flag_k != SpecialToken.FLAG_FINISHED`, lines [79-80](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/generation.py#L79-L80) set `carry = c_next` and `output.append(o_k)`.
  - If the model emits a malformed out-of-alphabet or special token (e.g. `[SEP] = 240`, `[PAD] = 241`, or byte `255`) for `o_k` or `c_next`, `build_step_ar_example` at step `k + 1` validates only `(alphabet, a, b)` via `build_prefix_tokens` and passes `carry` and `output` straight into `Example` (which accepts any `int` in `0..255`). Rollout therefore propagates the model's own corrupted `o_k` and `c_{k+1}` into step `k + 1` without crashing or consulting the oracle (also verified in [test_step_ar.py](file:///atelier/code/workshop/yessir/experiments/addition/tests/test_step_ar.py#L360-L410)).
- **Batch isolation, `model.eval()`, and scoring in `evaluate_step_ar` & `score_predictions`** (`variants/step_ar/` [evaluation.py](file:///atelier/code/workshop/yessir/experiments/addition/variants/step_ar/evaluation.py#L25-L129), `addition/` [evaluation.py](file:///atelier/code/workshop/yessir/experiments/addition/evaluation.py#L70-L222)):
  - Both `evaluate_step_ar` and `rollout_step_ar` are decorated with `@torch.no_grad()` and call `model.eval()` before running forward passes. The model has no dropout, BatchNorm, or KV-cache state across batches, and `evaluate_step_ar` indexes each row relative to its own unpadded `batch.lengths` (`batch.lengths + offsets[i]`), so `eval_batch_size` has zero effect on predictions (barring `float32` SIMD reductions, which are deterministic per shape).
  - In `evaluate_step_ar`, malformed tokens emitted at `t_0` or `t_1` (such as `[SEP]`, `[PAD]`, `[FLAG_FINISHED]`, or symbols outside `alphabet`) are unpacked into `StepPrediction(sum_digit=pred_o, carry_out=pred_c, halt_ok=(pred_flag == int(step.flag)))` (`syntax_ok` defaults to `True` because `step_ar` has no model-emitted structural header/query tokens; query tokens `[S]`, `[C]`, `[F]` are harness-injected). In `score_predictions`:
